## Architecture constraint

The existing relay forwards raw ADB to `127.0.0.1:5555`. Android's [ADB TCP restart implementation](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/daemon/restart_service.cpp) sets `service.adb.tcp.port`, a temporary property. Android 16 [property policy](https://android.googlesource.com/platform/system/sepolicy/+/android16-qpr1-release/private/property.te) restricts writes to ADB configuration properties to privileged system domains. Adding a boot receiver to an ordinary APK does not grant those privileges.

All in 0.7.0 adds Direct Boot support for the relay: LOCKED_BOOT_COMPLETED plus a Direct Boot aware foreground service. Only the machine relay's configuration and mTLS files move into app-private device-protected storage, with an initial unlocked migration required for existing installations. Explicit stop remains persisted. Android's [Direct Boot documentation](https://developer.android.com/privacy-and-security/direct-boot) distinguishes startup before first unlock from normal boot-completed startup. A secure lock and credential-encrypted Chrome account data remain separate readiness constraints. Browser credentials are not moved; Chrome/home endpoints reject launch before unlock. This change cannot restore privileged ADB TCP settings.

Device-owner enrollment alone is not a proven solution: the documented ADB_ENABLED setting concerns USB debugging, not a persistent TCP listener. Wireless debugging also uses a different, paired TLS transport; merely enabling its setting will not satisfy the current raw port-5555 relay.

## Next implementation decision

All in 0.8.0 prototypes a no-root alternative: a one-time USB-granted WRITE_SECURE_SETTINGS permission allows requesting Android's `adb_wifi_enabled` setting after unlock and Wi-Fi availability. Android must still approve the lab Wi-Fi network; the application cannot bypass that prompt. NSD discovers `_adb-tls-connect._tcp` and accepts only a listener whose advertised address belongs to this phone, forwarding to loopback. The relay carries the existing client's authorized TLS ADB connection, avoiding any need to restore fixed port 5555. Current prototype requires live TLS authorization and reboot validation; do not count successful socket probing as authenticated ADB readiness. See [Android's ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md). This corrects the earlier assumption that only privileged firmware could provide a usable recovery path; directly setting legacy TCP properties still requires privileges.

Select and validate a supported boot-time ADB capability for the intended lab hardware (for example an OEM/system-provisioned image with suitable permissions), or explicitly redesign browser/device control to remove the ADB dependency. Compatibility and provisioning cost must be established before choosing either path. No rooting, bootloader unlocking, firmware flashing, factory reset, or new privilege grant has been performed or assumed authorized.

## Diagnostic command

`node scripts/verify-reboot-readiness.mjs --reboot <enrolled-device-id>` requires authorized USB, checks the baseline, explicitly reboots, waits up to 120 seconds for identity/changed boot ID/completed boot, then allows 15 seconds for supervisor startup. It observes unassisted local state before attempting existing USB recovery. Reports contain no credentials. USB-assisted recovery is reported separately and cannot establish remote-only acceptance. A failure or missing local ADB returns a nonzero exit code. Even local success still requires the remote-only acceptance above.
